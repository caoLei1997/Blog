# 前端调试知识

调试的定义：**把运行时状态通过某种方式暴露出来，传递给开发者工具做 UI 的展示和交互**。

这篇文章从原理到实践梳理前端调试：DevTools 是怎么工作的、怎么用 VS Code 调试网页、launch.json 怎么配、sourcemap 又是什么。

## 1. 初识调试

**Chrome DevTools 原理（两部分：backend 和 frontend）**

- backend：和 Chrome 集成，负责把网页运行时状态通过协议暴露
- frontend：独立，对接协议，展示 UI 和交互
- 两者的协议：Chrome DevTools Protocol，简称 CDP
- 传输方式：信道 message channel，有多种方式
- 内置调试工具使用全局函数通信，远程调试使用 WebSocket 通信
- backend 可能是 Chromium、Node 或 V8

![Chrome DevTools 原理](https://cdn.nlark.com/yuque/0/2022/png/663644/1669877759819-db0bfb67-360c-4e92-80b7-ef8102857dfb.png)

**VS Code Debugger 原理（backend 和 frontend）**

原理和 Chrome DevTools 差不多，但多了一层适配器协议 Debug Adapter Protocol。

原因是 VS Code 编辑器并不是 JS 专用，它还需要调试其他代码（Python 等等）。

![VS Code Debugger 原理](https://cdn.nlark.com/yuque/0/2022/png/663644/1669878266704-f89acab4-ae93-42ca-bbe9-e6041ff08685.png)

**Vue/React DevTools（浏览器插件）**

浏览器插件机制：

- Content Script：可以访问页面，随页面启动生效
- Background：是后台运行部分，浏览器启动就生效了
- DevTools 类型浏览器插件还需要 DevTools Page
- DevTools Page 可以在当前 window 中注入 JS 的，通过 Background 拿到 Backend 中的组件信息并注入到页面中

![Vue/React DevTools](https://cdn.nlark.com/yuque/0/2022/png/663644/1669879477873-4cc66445-4893-4054-b312-8c374bf32d36.png)

**总结**

调试就是通过信道将运行时信息传递给开发工具，做展示和交互。

调试工具的共同特点：frontend、backend、调试协议、信道，四部分。

## 3. VS Code 配置详解

通过 create a launch.json file 可以快速创建 VS Code Debugger 配置文件。

前面说过 VS Code 在调试的时候多加了一层 Debug Adapter Protocol 适配协议。

Chrome: Attach / Chrome: Launch 则是代表浏览器调试：

- Chrome 代表 VS Code 需要使用浏览器适配
- Attach / Launch 代表调试的方式，其中只有 request 的不同
- Launch：是新启动一个本地服务调试浏览器
- Attach：如果本地已经有服务启动，可以用 Attach 连接调试

![launch.json 配置](https://cdn.nlark.com/yuque/0/2022/png/663644/1669949972487-5e2ec932-3ca5-4b33-aeaf-93c86cf6fba9.png)

**configurations 其他属性**

- `userDataDir`：用户数据目录。true 创建临时用户数据，false 使用默认用户数据，也可以指定一个路径，用户数据会保存在此目录下
- `runtimeExecutable`：调试服务启动的 Chrome 版本，默认启动的是 Chrome 稳定版，也可以启动 Canary 开发者版本
- `runtimeArgs`：调试浏览器启动参数 `string[]`。默认打开 Chrome DevTools：`'--auto-open-devtools-for-tabs'`；使用无痕模式：`'--incognito'`
- `sourceMaps`：映射源码，boolean
- `file`：指定调试某一个文件，一般适用于传统项目、静态服务型项目
- `sourceMapPathOverrides`：对 sourcemap 到的文件路径做一次映射，映射到 VS Code workspace 下的文件，这样调试的文件就可以修改了

![configurations 属性](https://cdn.nlark.com/yuque/0/2022/png/663644/1669951395877-3844a1b5-2623-4dab-ba7e-830c8fc58519.png)

**总结**

- Launch：调试模式启动服务浏览器
- Attach：连接某个已经启动的服务浏览器
- userDataDir：创建临时用户数据的目录，使用默认目录则关闭此选项
- runtimeExecutable：切换调试用的浏览器 stable、canary
- runtimeArgs：启动调试浏览器时的启动参数
- sourceMapPathOverrides：对 sourceMap 文件再次映射到 VS Code 中，这样就可以调试修改了

## 4. sourcemap 详解

sourcemap 是关联编译前后代码和源码，通过一个个行列号的映射。

```json
{
  "version": 3,
  "file": "out.js",
  "sourceRoot": "",
  "sources": ["foo.js", "bar.js"],
  "names": ["a", "b"],
  "mappings": "AAgBC,SAAQ,CAAEA;AAAEA",
  "sourcesContent": ["const a = 1; console.log(a)", "const b = 2; console.log(b)"]
}
```

1. `version`：sourcemap 版本
2. `file`：编译后文件
3. `sourceRoot`：源码根目录
4. `sources`：源码文件名
5. `names`：转换前变量名
6. `mappings`：sources 位置映射，通过 `;` 代表行，每一行可能有多个位置映射通过 `,` 分隔。比如 ABCDE 分别有不同含义：
   - （A）转换后代码列
   - （B）转换前源码文件，保存在 sources 里
   - （C）转换前源码行
   - （D）转换前源码列
   - （E）转换前源码变量
7. `sourcesContent`：每个 sources 对应的源码内容

ABCDE 这种编码方式叫做 VLQ 编码。

调试工具一般都支持 sourcemap 的解析，只要在文件尾部加上以下代码：

```js
//# sourceMappingURL = /path/to/source.js.map
```

编译工具在生成代码时也会生成 sourcemap。

![sourcemap 生成](https://cdn.nlark.com/yuque/0/2022/png/663644/1670316354736-e532ab1a-d949-46a9-93b7-a59b387672cb.png)

- AST 中会保留源码位置，这是 parser（解析器）在 parse 源码的时候记录的（源码位置）
- AST 转后会打印成目标代码，打印时一行一列地拼接，这时就有了目标代码位置（目标位置）
- 这两个位置相互关联就会是一个 mapping，这样就生成了 sourcemap
- sourcemap 对应格式编码生成麻烦，推荐使用 [source-map](https://www.npmjs.com/package/source-map) 包

**webpack 中使用 sourcemap 配置**

- eval-nosources-cheap-module-source-map
- hidden-source-map

**eval**

eval 的 API 是动态执行 JS 代码。

eval 怎么才能打断点？

解：只要在 eval 代码中加入 `//#sourceURL=a.js`，那么就会在浏览器生成一个 a.js，可以断点调试。

webpack 利用 eval 优化 sourcemap 生成的性能，比如指定 devtool：eval。

生成的所有代码都会被 eval 包裹，并且有 sourceURL 指定文件名。

![webpack eval devtool](https://cdn.nlark.com/yuque/0/2022/png/663644/1670318122486-c865d5ac-9ca1-407c-9615-e1b5a4ac38e6.png)

优点：快。

缺点：没有做源码的关联。

如果要关联源码需要开启 sourcemap devtool：eval-source-map。

**基础配置**

- `devtool: source-map | hidden-source-map | inline-source-map`，分别对应：独立 sourcemap 文件、不关联源码文件、以及内联 sourceMappingURL 文件
- `cheap`：只需要精确映射到行。优点快，但是会牺牲精度，因为没有精确到列
- `module`：需要调试最初源码，关联每一次 loader 的 sourcemap
- `nosources`：不生成 sourcesContent，减小 sourcemap 文件大小，但得保证文件路径准确；如果没找到文件路径还是会映射，但会增加 sourcemap 的体积

**总结**

学习到了 sourcemap 是通过 AST 前后关联源码和目标代码所生成的。

1. 日常开发调试会使用到 sourcemap，源码调试
2. 线上错误收集，线上报错会使用 sourcemap 映射源码，会单独上传 sourcemap 到错误收集平台
3. 生成的类型可以通过 sourcemap 关联到对应源码中的定义
